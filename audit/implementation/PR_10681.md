## Summary

Renames `native_invoke` to `native_invoke_signed` and changes its signature
from accepting pre-derived `&[Pubkey]` signers to `&[&[&[u8]]]` signer seeds.
The function now derives PDAs internally via `create_program_address`, using
the caller's own program ID. This prevents builtins from silently vouching
for arbitrary account addresses as signers.

## Implementation

### Before
```rust
pub fn native_invoke(
    &mut self,
    instruction: Instruction,
    signers: &[Pubkey],
) -> Result<(), InstructionError> {
    self.prepare_next_cpi_instruction(instruction, signers)?;
    // ...
}
```

### After
```rust
pub fn native_invoke_signed(
    &mut self,
    instruction: Instruction,
    signer_seeds: &[&[&[u8]]],
) -> Result<(), InstructionError> {
    let caller_program_id = *self
        .transaction_context
        .get_current_instruction_context()?
        .get_program_key()?;
    let signers = signer_seeds
        .iter()
        .map(|seeds| Pubkey::create_program_address(seeds, &caller_program_id))
        .collect::<Result<Vec<Pubkey>, PubkeyError>>()
        .map_err(|e| e as u64)?;
    self.prepare_next_cpi_instruction(instruction, &signers)?;
    // ...
}
```

## Security Analysis

### 1. Signer Privilege Escalation Prevention

**PASS.** The old API (`native_invoke(&[Pubkey])`) allowed any builtin to
pass arbitrary pubkeys as CPI signers without proof of authority. The new
API (`native_invoke_signed(&[&[&[u8]]])`) forces derivation via
`create_program_address(seeds, &caller_program_id)`, which:
- Only produces PDAs derived from the calling program's own ID
- Cannot produce arbitrary user wallet addresses (non-PDA pubkeys have
  no valid seed derivation)
- Mirrors the SBF `invoke_signed` path exactly

### 2. Feature Gate Requirement

**PASS — no feature gate needed.** The semantic behavior is unchanged for
all callers:
- Call sites that passed `&[]` (no signers) continue to pass `&[]` (no seeds)
- The one bpf_loader site that derived a PDA before passing it now passes
  the raw seeds instead — the derived address is identical
- No on-chain program behavior changes; this is a compile-time API change
  in the runtime, not a consensus change

### 3. Error Handling

**Acknowledged known issue.** The `PubkeyError` to `InstructionError`
conversion uses `map_err(|e| e as u64)` which maps through num-traits and
produces `InstructionError::Custom(0)` for `MaxSeedLengthExceeded`. This
is preserved from the old code, documented with a comment, and pinned by
a test (`test_native_invoke_signed_with_invalid_seeds` asserts
`Custom(0)`). Not a new issue — it's the existing behavior carried forward.

### 4. `prepare_next_cpi_instruction` Visibility

**Minor concern (noted by agent).** `prepare_next_cpi_instruction` remains
`pub` and still accepts `&[Pubkey]`. A future builtin author could call it
directly, bypassing `native_invoke_signed`. The function is legitimately
needed by the SBF CPI path (`cpi.rs`) and `program-test`. The doc comment
on `native_invoke_signed` states the security property, but the raw API
remains accessible. Not a vulnerability today — all current callers use the
safe path.

### 5. Test Coverage

**Comprehensive.** Five targeted tests:
1. Valid PDA signer succeeds
2. Oversized seeds return `Custom(0)` (pinning the known-bad error mapping)
3. Missing seeds cause `PrivilegeEscalation`
4. Seeds for wrong program ID cause `PrivilegeEscalation`
5. Top-level transaction signers carry through without needing seeds
