## Summary

Extracts deployment functions from `programs/bpf_loader/src/lib.rs` into a
new `program-runtime/src/deploy.rs` module. Moves `morph_into_deployment_environment_v1`,
`load_program_from_bytes`, `deploy_program`, and the `deploy_program!` macro.
The metrics parameter is gated behind `#[cfg(feature = "metrics")]` in the new
location.

### Category B: Structural Changes

**Metrics parameter refactored behind `#[cfg(feature = "metrics")]`:**

`load_program_from_bytes` and `deploy_program` now take the
`LoadProgramMetrics` parameter only when the `metrics` feature is enabled:

```rust
// Old (always present):
pub fn load_program_from_bytes(
    log_collector: ...,
    load_program_metrics: &mut LoadProgramMetrics,
    ...

// New (feature-gated):
pub fn load_program_from_bytes(
    log_collector: ...,
    #[cfg(feature = "metrics")] load_program_metrics: &mut LoadProgramMetrics,
    ...
```

All `Measure::start()` / `.stop()` / metric field assignments are also
gated behind `#[cfg(feature = "metrics")]`.

**`deploy_program` return type changed:**

| | Old | New |
|--|-----|-----|
| Return | `Result<LoadProgramMetrics, InstructionError>` | `Result<(), InstructionError>` |
| Metrics creation | Internal (`LoadProgramMetrics::default()`) | External (caller passes `&mut`) |

The `deploy_program!` macro now creates `LoadProgramMetrics::default()` and
passes it in, then calls `submit_datapoint` — exactly what the old callers
did with the returned value. The `core_bpf_migration` call site also creates
metrics externally now.

**`loader-v4` feature flags added:**

`default = ["metrics"]` and `metrics = ["solana-program-runtime/metrics"]`
added to `programs/loader-v4/Cargo.toml`. This ensures loader-v4 gets the
metrics-enabled version by default, matching the prior behavior where metrics
were always compiled in.

### Category C: Behavioral Changes

**None.** When the `metrics` feature is enabled (which is the default for
all crates that use these functions), the behavior is identical:
- Same ELF loading and verification pipeline
- Same error types (`InstructionError` variants throughout)
- Same program cache operations
- Same `morph_into_deployment_environment_v1` logic (reject_broken_elfs,
  sol_alloc_free filtering)
- Same metrics collection and datapoint submission

When the `metrics` feature is disabled, the only difference is that timing
measurements are skipped. This does not affect deployment correctness,
security, or consensus.
